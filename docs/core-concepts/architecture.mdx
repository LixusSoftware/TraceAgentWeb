# Architecture

TraceAgent follows a **client-server** architecture with a modular package design. Understanding how the pieces fit together helps you make the most of the platform.

## System Overview

## Package Breakdown

### TraceAgent SDK

The core Python client. Use it to:

- **Start and finish runs** — Create named sessions with descriptions
- **Record file operations** — Reads, writes, patches, and diffs
- **Record commands** — Shell executions with exit codes
- **Record tool calls** — Custom tool invocations with parameters and results
- **Attach artifacts** — Any derived output from the agent

The SDK communicates with the server via REST API calls.

### TraceAgent LangChain

A **callback handler** that plugs into LangChain's callback system. Once attached, it automatically captures:

- Chain starts and completions
- LLM calls (prompts and responses)
- Tool usage and results
- Retriever activity
- Error states

No manual instrumentation needed — just pass the callback.

### TraceAgent Pydantic AI

A **capability** for [Pydantic AI](https://ai.pydantic.dev) 2.x agents. Add it to your agent and it records model calls and tools without blocking the agent. See [Pydantic AI Integration](/docs/instrumentation/pydantic-ai).

### TraceAgent Server

The **FastAPI backend** that persists and serves trace data:

- Receives events from the SDK, the LangChain handler and the Pydantic AI capability
- Receives OpenTelemetry traces at `POST /v1/traces`
- Stores data in **SQLite** (default) or **PostgreSQL**
- Exposes REST API for the UI to query
- Supports audit metrics collection

### TraceAgent UI

The **interactive dashboard** for visualizing traces:

- Execution timelines with event details
- Run listings with search and filtering
- File diff viewer for recorded edits
- Artifact browser

## Data Flow

1. Your agent code calls the **SDK** (or uses the **LangChain callback** or the **Pydantic AI capability**)
2. The integration sends events over HTTP to the **Server**
3. The Server persists events in the **database**
4. The **UI** queries the Server API and renders visualizations

The server also exposes an OTLP/HTTP receiver at `POST /v1/traces`. Spans that follow the GenAI conventions are turned into the same runs and events as the SDK and framework integrations, so agents can be traced without TraceAgent code. See [OpenTelemetry Ingestion](/docs/instrumentation/opentelemetry).

## What a Run Shows

A run shows what the agent actually did, not just a list of events. Each run records the provider, the model and the token usage of its model calls.

Tools appear under the agent step that used them, so the timeline is nested: the agent run contains its model calls and tools, in the order they happened, and nested agents appear inside the step that called them. The inspector shows what happened in plain terms (result, duration, tool, tokens, error) and keeps identifiers and raw data under "Technical details".

The first level opens by itself, and **Expand all** and **Collapse all** open or close every step. A tool row shows its arguments, and a command step is titled by the first comment of its script.

![Nested timeline of an agent run: model calls, tools with their arguments, the command one of them ran, and the final output](/img/trace-agent/timeline-nested.jpg)

When a run finishes or fails, TraceAgent derives its **decisions** (which tool was chosen, retries, recoveries) and flags such as loops. They are not shown while the run is still running. Each decision lists the events it is based on.

![Decision graph of a run where a tool failed, was retried and recovered, with the events behind the retry](/img/trace-agent/decisions-retry.jpg)

The UI updates live while the agent is running.

A **model call** is titled with the real model (`Model call · <model>`). Select it to see its prompt, with the instructions first as SYSTEM, and its response. Object outputs are shown as JSON.

![Inspector of a model call showing its prompt and response](/img/trace-agent/model-call-inspector.jpg)

The **execution graph** has one node per step:

![Execution graph of a run with one node per step](/img/trace-agent/execution-graph.jpg)

Flags avoid false alarms. A loop is flagged only when a tool is called several times with the same arguments (compared by their hash), so an agent that corrects itself is not flagged. It is flagged once, with its count: `X was called N times with the same arguments.` A failed command reads `Command failed (exit code N): <first comment>`, and tracebacks keep their line breaks. **Steps** counts only top-level actions.

Events are ordered by arrival, not by wall-clock time. A command recorded inside a tool can appear before its tool row, but it is nested under it.

:::info[Self-hosted]
All data stays on your infrastructure. There's no external telemetry, no cloud dependency. You own everything.
:::
